# framework/ — the C4 video framework (options 1 + 2)

This is the seed of a small video framework. Nick chose two of the four POC
approaches, option 1 (Code Hike + Remotion) and option 2 (Motion Canvas). This
tree keeps the code worth keeping from both and arranges it around one rule:
**everything except drawing lives in core, once.** A later pass lifted the
ideas worth keeping from options 3 and 4 (see § "Lifted from options 3 and 4").

```

    src/storyboard/           schema.ts (types, c4v-storyboard/1) · validate.ts (pure, incl. arc rules)
    src/beats/                registry.ts (BEATS: role → kinds, needs, checks) · patterns.ts (PATTERNS)
    src/ingest/               repo.ts (git log facts) · blame.ts (blame over shown excerpts) · types.ts
    src/narration/            elevenlabs.ts (with-timestamps client) · takes.ts (committed takes)
```

## The boundaries

```
 storyboard.json ─┐
 dataset snapshot ├─► core: c4v build ─► build/bundle.json ─┬─► renderer-remotion       ─► renders/remotion.mp4
 narration takes ─┤   (validate, pin,    build/track.wav   └─► renderer-motion-canvas  ─► renders/motion-canvas.mp4
 git @ commit ────┘    layout, retime, mix)
```

- **The storyboard** says what to show and what is said. It holds no timings.
  Scene kinds are `architecture-overview`, `focus-element`, `follow-request`,
  `state-change` and `code-explanation`, plus the story-arc cards `repo-card`
  and `credits` (§ "Story arcs"). Code scenes use either `focus`
  (cue-timed selections) or `steps` (a stepped walk voiced as one take). A
  scene says exactly one of a `caption`, `steps` or `lines` (several
  separately voiced lines). Each spoken line has a `caption` (shown on
  screen) and an optional `speech` (sent to TTS). Animation cues are named
  phrases of the spoken text; each phrase must occur exactly once in its
  scene. Optional `acts` group scenes; excerpts may pin their own commit and
  may be `evidence` (recorded results or prose) instead of code.
- **Core** does all of the following, and nothing else does:
  - validates the storyboard against the dataset's model and views;
  - pins every excerpt from git objects;
  - lays out every view it needs with elkjs;
  - turns the takes' alignment into the **timeline**: frame-exact scene
    placement, take placement, cue times, step and act bounds, and captions,
    and checks the timeline's invariants;
  - mixes one narration track;
  - answers every timing question renderers ask (`play.ts`), including which
    context diagram a code scene keeps, when its code pane enters and which
    edge a hop lights;
  - proves each finished MP4 against the timeline (`c4v proof`).
- **A renderer** reads `build/bundle.json` and plays `build/track.wav`, and
  reads nothing else. It never opens the storyboard file, the dataset, git or
  the takes, and it contains no hard-coded coordinates, code or times. Both
  renderers ask `play.ts` (`focusOf`, `hopsOf`, `stateAt`, `captionAt`, …) so a
  highlight or a hop lands on the same word in either engine. `grep` over both
  renderers' `src/` and `scripts/` for storyboard, alignment, git, ElevenLabs
  or secrets reads finds none.
- **Data in, dumb views, logic in pure functions.** `projectView`,
  `buildTimeline`, `validateStoryboard`, `hopPath`, `along` and everything in
  `play.ts` are pure. The node-only edges are git, ffmpeg, elkjs, fs and fetch,
  and they sit in separate modules that `index.ts` does not export.

### Unified retiming (the better ideas of both POCs)

`narration/timeline.ts` replaces both POC narrate scripts.

- **From option 2:**
  - Scene length is measured to the **last spoken letter**, not the closing
    punctuation, whose alignment span is up to 1 s of trailing silence.
  - Lengths are rounded up to whole frames.
  - Cues are anchored on phrases.
  - The take text is checked 1:1 against its alignment.
  - The mix guard (`track.ts`) refuses any cut that would drop speech.
  - TTS requests send `previous_text` and `next_text` so separate takes keep
    continuous prosody.
- **From option 1:**
  - A stepped scene is voiced as one take. Each step lights `stepLead` (0.25 s)
    before its first word, found by its offset in the stitched text.
  - Lead-in can be overridden per scene.
  - `minDuration` covers moves that need time, such as the focus zoom.
  - A stale take is refused: if the storyboard text no longer matches, the
    take is not reused.
- **From option 3** (the idea, not its code): a scene may say several lines,
  each its own take, chained `narration.lineGap` (default 0.4 s) apart and
  each measured to its last spoken letter. Each take is cut where the next
  starts. A cue phrase is looked up across all of a scene's lines and must
  occur exactly once, so it can never bind to the wrong line or the first of
  two matches.
- **Evidence** (`npm test` in core):
  - The 11 option-2 scenes come out frame-identical to option 2's
    `timeline.json`, with identical cues.
  - The acquire steps reproduce option 1's 4.88 / 8.27 / 7.38 / 7.73 s.
  - The last step is shorter than option 1's 5.43 s (5.14 s) because of the
    last-letter fix.

## How to render each demo

```sh
export PATH="$HOME/.nvm/versions/node/v22.23.2/bin:$PATH"     # Node 22.23.2
cd framework/core && npm ci
node bin/c4v.ts build  ../projects/litefleet    # offline; never calls ElevenLabs
node bin/c4v.ts verify ../projects/litefleet    # fidelity, timeline invariants, reproducibility
npm run typecheck && npm test

cd ../renderer-remotion && npm ci && npm run typecheck && npm test
flock /tmp/c4v-render.lock node scripts/render.mjs ../projects/litefleet    # --concurrency=2
flock /tmp/c4v-render.lock node scripts/stills.mjs ../projects/litefleet

cd ../renderer-motion-canvas && npm ci && npm run typecheck && npm test
flock /tmp/c4v-render.lock node scripts/render.mjs ../projects/litefleet > /tmp/mc-render.log 2>&1
node scripts/stills.mjs ../projects/litefleet

cd ../core && node bin/c4v.ts proof ../projects/litefleet   # both MP4s against the timeline
```

- Each renderer's `render.mjs` already fails unless its MP4 passes
  `proveOutput`; `c4v proof` re-checks committed renders at any time.

- `c4v build` needs the book-notes checkout at `/root/Software/book-notes`, or
  set `C4V_CHECKOUT_BOOK_NOTES`.
- `c4v narrate <project>` is the only command that spends TTS credits, and only
  for scenes that have no take. This run voiced 0 characters.
- The ElevenLabs key is read from `/root/Software/.secrets/c4-video.env` at
  call time, or from `C4V_SECRETS`.
- The story-arc video renders the same way; see § "Story arcs".
- Each renderer's own notes are in `renderer-motion-canvas/README.md` and in
  the scripts' header comments.

## Story arcs (2026-10-24, the first arc video)

Design: [../docs/story-arc-plan.md](../docs/story-arc-plan.md). This build
landed plan items 1, 2 (Remotion only), 3, 4 and 6, and a thin slice of 5,
and used them to make `projects/litefleet-arc`, "One query's guardrails".
The `gains` beat is deferred (plan § 10): its role is reserved and nothing
else of it exists.

- **Arc schema, registry, patterns (item 1).** `Storyboard.arc` (`pattern`,
  `beats`, `chrome`) and `Act.role / variant / optional` are optional
  additions to `c4v-storyboard/1`. `beats/registry.ts` `BEATS` is the one
  place a role is spelled out (allowed kinds, needs, extra checks);
  `gains` and the four change-pattern roles are entries with `kinds: []` and
  a `reserved` reason, so naming one fails with "deferred" or "reserved", not
  "unknown". `beats/patterns.ts` holds `walkthrough` (repo-intro,
  architecture, focus, deep-dive required; shoutout optional).
  `validateArc` (run by `validateStoryboard`) checks beats are roled acts in
  act order, acts outside the arc are optional, the pattern's required roles
  are present and in slot order, each beat holds only its role's kinds, and
  the role's own checks (a repo-intro opens on a repo-card; a focus beat has
  one focus-element; every deep-dive excerpt is tied to the focus element by
  `elementId` or a lit context). `timeline.acts[].role` is carried, and
  `play.ts` `arcProgressAt(bundle, t)` returns each beat's state, the current
  index and progress. An arc-less storyboard is unchanged: litefleet's
  committed `build/bundle.json` rebuilds byte-identically.
- **Act chrome (item 2, Remotion).** `renderer-remotion/src/LowerThird.tsx`
  is a chrome layer in `Walkthrough.tsx`, drawn above the captions in the new
  `LOWER_THIRD` box (y 614–640, between the content regions and a one-line
  caption). One chip per beat, the current one lit with a progress line;
  bright as a beat starts, settling back after ~3 s. It reads only
  `arcProgressAt`. `arc.chrome.lowerThird: false` turns it off, `labels:
  "role"` shows roles instead of act titles.
- **repo-card (item 3).** A `repo-card` scene names the system element and a
  `facts` list; `play.ts` `repoFactsOf` turns `bundle.repo` into label/value
  rows, so the card prints nothing typed. Remotion draws it over its view,
  dimmed, and the next scene on that view brings the diagram forward.
- **Repo ingestion (item 4).** `ingest/repo.ts` reads, from git objects at
  the pin and scoped to `sources.code.stripPrefix`: commit count, first/last
  author dates, tags merged into the pin whose commit touches the scope,
  authors by commits, files by extension, and C4 model counts from the
  dataset. `c4v build` writes it as `bundle.repo` when a beat needs `git-log`;
  `c4v verify` re-ingests and fails if it does not reproduce.
- **Descend and responsibilities (item 6).** `architecture-overview` gains
  `descend: {elementId, cue}` (light it on the cue, dive into it as the scene
  ends; `validateRefs` requires the next scene to show its
  `detail.diagramId`) and `settle` (light it and let the camera rest on it,
  for the last level). `focus-element` gains `responsibilities: {label,
  cue}[]`, each item appearing on its cue (`responsibilitiesOf`). After a
  `settle` on the same element the focus camera holds instead of re-zooming.
  `approachOf` gives both renderers the same timing. *Deviation:* the plan
  sketched `responsibilities?: string[]` fed by caption lines; labels with
  cue phrases keep the list short and timed by the existing cue contract.
- **Thin credits (slice of item 5).** `ingest/blame.ts` runs `git blame
  --porcelain` over exactly the code excerpts a scene shows, each over its
  range at its own pin, and records each blamed commit's author, subject,
  date and `Co-authored-by` trailer names (`bundle.credits`). The `credits`
  scene kind prints `creditLine` (the video's commit: `tag · sha7 · subject
  · date`), author rows with share bars and the commits behind the lines,
  via `videoCreditsOf`. `names` on the scene must appear in a caption and be
  a blamed author (build and verify). Not built: `creditsOf` scopes and
  aggregation, `.mailmap` folding, aliases, per-excerpt bylines.
- **Narration fix.** `c4v narrate` now creates `narration/` before its first
  billed call; it used to lose the first take of a new project.

Notes and deviations, per item:

1. Checks: H.264 + AAC streams; the timeline's size and fps; exactly
   `totalFrames` packets; audio within 0.1 s of the video; moov before mdat; a
   full `ffmpeg -map 0 -f null` decode with empty stderr; under 10 MiB.
   Loudness is computed in JS from the decoded track (the same mean power
   `volumedetect` reports) rather than by one ffmpeg run per window. Each
   line, or each step of a stepped scene, must average above −35 dB inside
   its speech window. Every pause of 0.2 s or more must stay below −45 dB,
   measured from 0.1 s after a line's last letter to 0.05 s before the next
   line, so codec ramps are not counted. Option 3's footage asserts are
   dropped. The loudness rules assume narration only, with no music bed.
   Motion Canvas's ad-hoc probe is replaced by the shared proof.

   in the salvage run. `Walkthrough` maps every timed scene through
   `SCENE_KINDS` and reads core's timeline, not fields written back into the
   storyboard. Scenes are typed by core's `Scene` union. One mixed track
   replaces option 3's `<Audio>` per line. Nothing was re-implemented.

   drift. The expected SHAs come from the storyboard, not a literal map. The

   offset, which is more exact than a cue). New: `acts` + `scene.act`

### The salvage run's proposed core changes

All three were clean to implement and are in core now:

- **Context inheritance** → `contextAt` (schema) / `contextOf` (play.ts).
  Both renderers' copies were deleted, and `validateStoryboard` now checks
  hops against the inherited context.
- **Code-pane entry cue** → `CodeScene.enter` + `codeEnterOf`. Litefleet's

  already did.

## Seams left for story-arc components

A follow-up planning run should design against these seams. Each one is named
where it lives.

1. **Scene-kind vocabulary** (`core/src/storyboard/schema.ts`, `Scene` union and
   `DIAGRAM_KINDS`). A new arc beat, such as "test evidence" or "before/after
   diff", starts as a new kind here, plus validation in `validate.ts`.
2. **Renderer scene registries.** A new kind is one entry in each registry, and
   the interpreters stay generic:
   - Remotion: `SCENE_KINDS` in `renderer-remotion/src/scenes.tsx`. A kind's
     `shot()` returns the diagram, code pane and panel state, plus an optional
     per-scene `Overlay`.
   - Motion Canvas: `RUNNERS` in `renderer-motion-canvas/src/kinds.tsx`, over a
     `Shot`.
3. **Playback queries** (`core/src/play.ts`). Any new timed behaviour is a pure
   query here, consumed by both renderers, and never a per-renderer
   re-derivation.
4. **Cue contract** (`narration.cues` → `timeline.scenes[].cues`). Story-arc
   components hang animation on named spoken phrases, and anchors are checked at
   build time.
5. **Transitions and camera.**
   - Remotion: `camera.ts` (`cameras`), `stage.ts` (screen regions), and
     `TRANS`/`fadeIn`/`fadeOut`.
   - Motion Canvas: `Stage.transition(shot)`, `CameraTarget` and
     `DiagramView.shoot`.

   Today the rule is a camera move for the same view and a crossfade for a
   different view. An arc layer would choose transitions explicitly.
6. **State and overlay layer** (`statePanel` + `state` changes). This is the
   generic "what the system holds right now" overlay, with text, counter and
   slots kinds. New overlay kinds (queues, logs, metrics) extend `StateField`.
7. **Arc grouping.** `Storyboard.acts` + `scene.act` exist now (audit-34
   lift 5): acts are validated contiguous, `timeline.acts` carries their
   bounds, and `actAt` answers which act is playing. An `arc` over the acts,
   the beat registry and the Remotion act tracker are built (§ "Story arcs").
8. **Storyboard producer** (AI mapping). It must emit `c4v-storyboard/1`, and
   `validateStoryboard` + `c4v verify` are its acceptance gate.
9. **Excerpt resolution** (`code-source/excerpts.ts`). Excerpts are raw line
   ranges checked against a symbol today, each at its own pin (`at`), as code
   or as evidence. A Tree-sitter resolver (symbol → range) plugs in before
   `pinOne`. Audit item 11 (code-evolution beat) would list excerpt ids of one
   symbol across pins; `exportTree` serves scenes that run pinned code.
10. **Narration provider** (`narration/elevenlabs.ts` behind `takes.ts`). Another
    TTS or a pronunciation lexicon swaps in here, and the timeline only needs
    `Alignment`.
11. **Project inputs** (`checkoutFor`, `sources.dataset.snapshot`). On the
    platform these point at the sandbox clone (see `docs/platform-canvas.md`).
